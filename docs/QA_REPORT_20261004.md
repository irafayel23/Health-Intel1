## Initial findings (resolved locally)

### 1. P2 — Newborn age zero is shown as missing

**Locations:** `assets/js/bhw/bhw-residents.js:83`; `assets/js/admin/admin-records.js:40` and `:123`.

Reproduction: save a synthetic case with birthdate equal to its recorded date. Both the patient API and resident dossier API return numeric age `0`. The resident directory correctly says `0 yrs`, but the BHW dossier says `N/A yrs old`, and the Admin patient table says `N/A`.

The expressions `data.age || "N/A"` and `p.age || "N/A"` treat a valid zero as missing. Use an explicit null/undefined fallback, such as `age ?? "N/A"`, consistently. This is a presentation defect; the stored age was correct in the reproduced case. Add a targeted boundary regression test for zero and missing age.

Evidence: `age-zero-api.json`, `bhw-320-light-newborn-dossier.png`.

### 2. P2 — BHW dossier leaves keyboard focus behind the overlay

**Locations:** `bhw.html:370`; `assets/js/bhw/bhw-residents.js:123–137`.

Reproduction: open Patient Records → Profile. The modal appears, but focus remains on the underlying Profile button. Press Escape: the dossier stays open. Press Tab: focus moves to the underlying Update Status button. Reproduced in dark desktop and light narrow mobile views.

The custom overlay lacks dialog semantics and an accessible title, initial focus, a focus trap, background isolation, Escape handling, and focus restoration. A keyboard user can interact with obscured case actions while the dossier is open. The icon-only close button also has no accessible name.

Recommended fix: reuse the established accessible dialog pattern or implement those behaviors while retaining the existing IDs/hooks. The Admin Add to Registry overlay (`admin.html:392`, `assets/js/admin/admin-registry.js:68`) also opens without dialog semantics or moving focus and should receive the same treatment. The SweetAlert case-history and account-history dialogs do move focus to their Close button.

Evidence: `bhw-profile-dark.png`, `bhw-320-light-newborn-dossier.png`, `admin-mobile-dark-add-disease.png`.

### 4. P2 — MHO comparison titles and chart labels become too dim in dark mode

**Locations:** `assets/css/shared/mho.css:215–218`; `mho.html:249` and `:264`; `assets/js/bhw/bhw-dashboard.js:48`; `assets/js/mho/mho-analytics.js:38`, `:43`, `:93`, `:128`.

The MHO comparison headings inherit the fixed `.panel-title` color `#475569` on a near-black dark card, measured at **2.64:1**. The heading text remains dark even when surrounding page text switches correctly. This was verified after theme and chart rendering settled.

BHW and MHO canvas chart ticks/legends also remain gray in dark mode. Chart configuration does not specify theme-aware tick/legend colors, and the theme controls do not update chart colors. This canvas observation is visual; the DOM contrast audit does not measure individual canvas glyphs.

Recommended fix: give `.panel-title` a dark-theme foreground and update existing Chart.js instances' tick, legend, empty-state-title, and grid colors when the theme changes. Verify populated and empty charts in both modes.

Evidence: `mho-desktop-dark-comparisons.png`, `mho-desktop-dark-chart-settled.png`, `bhw-dark-chart.png`.

### 5. P2 — Several controls are unnamed or unavailable through normal keyboard navigation

**Locations:** theme buttons at `bhw.html:112`, `mho.html:118`, `admin.html:108`, `superadmin.html:76`; account avatars at `bhw.html:119` and `mho.html:124`; registration return control at `index.html:172`.

All four theme controls contain only decorative icons and expose no accessible name. The BHW and MHO account-settings controls are clickable `div` elements without keyboard focus or button semantics. The registration “Cancel and return to Login” control is an anchor without `href`, role, or tabindex, so it is absent from normal link/keyboard navigation.

Recommended fix: use native buttons for actions, retain IDs and onclick hooks, and add accurate accessible labels to icon-only buttons. Ensure account settings and registration cancellation can be reached and activated with a keyboard. No account credentials were changed during the review.

### 6. P3 — Theme selection is lost on reload

**Locations:** `assets/js/admin/admin-shell.js:5`; `assets/js/bhw/bhw-shell.js:5`; `assets/js/mho/mho-shell.js:23`; `assets/js/superadmin/superadmin-shell.js:5`.

Browser reproduction: switch Admin to dark mode and reload; it returns to light mode. All four handlers only change the current document and do not persist a theme preference; Superadmin starts with its own dark default. This is a UX inconsistency rather than data loss.

Recommended fix: share one saved preference and initialize it before the page paints. Decide whether the desired behavior is one application-wide choice or a separate choice per portal.

### 7. P3 — Superadmin dialogs remain dark while the page is in light mode

**Location:** `assets/css/superadmin/superadmin-page.css:17–22`.

The backup dialog stays dark when opened from the light-mode page because SweetAlert colors are unconditional `!important` overrides. It remains usable, but the theme is inconsistent with the rest of the interface. Scope dark overrides under `.dark` and provide the corresponding light appearance.

Evidence: `superadmin-320-light-backup-dialog.png`, `superadmin-320-dark-backup-dialog.png`.

## Existing prediction and defense limitations

The prediction work remains a separate validation task. `server/analytics.py` identifies the model as **AR(1)** and its validation as **pending**. A successful request does not establish accuracy on the intended final-defense dataset.

- The prediction disease dropdown is hardcoded (`mho.html:306–316`), so a newly approved registry category does not automatically become a forecast option. This is a confirmed interface limitation; whether it is a requirement defect depends on which diseases the final model supports.
- `server/analytics.py:28` checks `status != 'Archived'` rather than the separate archive flag. That deserves correction before model validation because current archival uses a separate field.
- `server/analytics.py:41` fills absent monthly observations with zero; incomplete reporting and genuine zero cases need to be distinguished for defensible analysis.
- The Python process reads MySQL directly, which remains at odds with the stated isolation direction in `docs/AGENTS.md`.
- This review did not transfer the local dataset to Azure, stress-test concurrent predictions, validate forecast accuracy, run a recovery drill on the live VM, or obtain MHO acceptance of report formats.

The listed UI fixes and their regression/visual checks are complete locally. Next, rehearse the final login → record → dashboard → prediction → report flow using the intended approved dataset.
